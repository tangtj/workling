# 独立评审

## 目标

workling 交付 PR 之后，再由一次独立的运行评审这个 PR：自己重跑检查、逐条核对验收、通读改动及其调用方，给出结论和逐条发现。最终目的是让「能不能合并」不再只靠人看，并把发现的问题直接送进已有的返工闭环。

现在的问题：

- 交付质量只有两道保证：Pi 对 codex 回报的核对，和仓库 CI。两者都不是独立视角，Pi 的核对以 codex 的回报为线索。
- 本仓库 49 个 workling PR 没有一条正式 review，一半以上在创建后 5 分钟内合并。问题都是合并后在使用中才发现的。

## 试跑结论

写本文之前，用 4 个历史 PR 做了本地试跑：每个 PR 一份停在合并提交、不含后续历史的副本，由 codex 只读评审，两个模型各一次。

| 已知问题（后来的修复）                              | 评审的 PR | 较强模型 | 较弱模型 |
| --------------------------------------------------- | --------- | -------- | -------- |
| 上游在下游运行中合并，交付无限重试（#116）          | #98       | 抓到     | 漏掉     |
| 同上                                                | #93       | 抓到     | 抓到     |
| 从过期的文档分支切出（#96）                         | #93       | 漏掉     | 漏掉     |
| 分诊把主 Issue 误判为信息不全（#114）               | #93       | 漏掉     | 漏掉     |
| 返工失败把已完成的 Issue 改成失败、标签残留（#100） | #73       | 漏掉     | 漏掉     |
| 对照组：没有已知问题                                | #117      | 判为阻断 | 判为阻断 |

由此得到的设计约束：

1. **评审有用，但结论不能直接当关卡**。对照组也被判了阻断，严重度普遍偏高。必须先以影子级运行，积累「评审说了什么」与「人实际怎么处理」的对照数据，再决定自动动作的门槛。
2. **评审要自己运行检查命令**。只读代码时，「检查通过」这类验收项只能记为无法确认，全是噪音。
3. **评审要知道实现方已经声明的未完成项**，并把重复的发现标出来，不当作新发现。
4. **部分完成的 PR 也要评审**。试跑的 4 个样本里 3 个是部分完成，而且都被合并了。
5. **评审默认使用更强的模型和更高的推理强度**。单次只多几分钟，成本可以接受。
6. 评审抓不到「新功能与另一个已有功能相互影响」这类问题，它们不在 diff 里。这类问题留给后续的需求拆解阶段处理，不在本文范围内。

## 已定的规则

1. **评审是一次 worker 运行**（`kind: 'review'`），在与实现相同的执行器里运行，同样不持有 GitHub 凭证。原因：要执行仓库的检查命令（第三方代码），要用 codex 通读仓库，输入（Issue、diff）不可信。
2. **评审只读**。不提交、不推送、不建 PR；产出只有 `out/review.json`。
3. **评审运行不进入 Issue 的状态机**。它不改变 `issues.status`、`issues.lastRunId` 和状态标签，由独立的 `reviews` 表排队和记录。现有按「最近一次运行」做判断的逻辑（门控、返工批次、堆叠变基、控制台阶段）都不受影响。
4. **触发**：实现或返工运行成功交付（完成或部分完成，PR 已建或已更新）后，自动排一次评审。答复运行不触发。
5. **评审结论不靠轮询 GitHub 回流**。带 `<!-- workling -->` 标记或机器账号的内容会被反馈采集判为 `self` 并忽略，这是防自我循环的既有约定；并且 GitHub 不允许对自己开的 PR 提 Request changes。因此评审结论由主体直接读 `out/review.json` 落库；后续阶段要触发返工时，由主体直接写入 `feedback` 表。
6. **分级放开**，按仓库配置，沿用分诊的做法：`off` → `shadow`（只记录）→ `comment`（发到 PR）→ `auto`（触发返工）。
7. **只支持 GitHub**。

## 分阶段

| 阶段 | 内容                                                                                                           | 文档                                                 |
| ---- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1    | 契约与 worker：`review` 运行类型、`out/review.json`、评审约定、评审样例                                        | [stage-1-worker-review.md](stage-1-worker-review.md) |
| 2    | 影子级：交付后自动排评审、拉起与对账、结论落库、Issue 详情页展示                                               | [stage-2-shadow.md](stage-2-shadow.md)               |
| 3    | 评论级：把结论发到 PR（一条汇总评论，行内发现附文件与行号）                                                    | 待阶段 2 积累数据后再写                              |
| 4    | 自动级：达到门槛的发现写入 `feedback` 触发返工，返工后再评审，有轮数上限；主 / 子 Issue 链等评审通过再放行下游 | 待阶段 2 积累数据后再写                              |

阶段 1 做完后，不启动主体就能用 `workling-worker` 对一个准备好的目录跑出评审结论，用来调提示词和比较模型。阶段 2 做完后，线上每个交付都会得到一份评审记录，但 GitHub 上看不到任何变化。

阶段 3、4 的门槛（哪个严重度发评论、哪个严重度触发返工、是否过滤实现方已声明的问题）依据阶段 2 的对照数据决定，现在不定。

## 不做

- 不评审非 workling 开的 PR，不提供手动触发评审的标签或指令。
- 不评审人直接推到 PR 分支上的提交；只在 workling 自己交付后触发。
- 不做自动合并。
- 不在主体里直接调用 LLM 做评审（只看 diff、不跑检查的轻量做法）；试跑表明有价值的发现都来自阅读调用方和相邻模块。
- 不改实现与返工的提示词，评审结论在影子级不进入实现方的任何输入。
