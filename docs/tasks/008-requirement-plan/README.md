# 需求拆解

## 目标

让 workling 接手「需求 → 设计文档 → 子 Issue」这一段：人只写一个粗需求 Issue，workling 读仓库、写设计文档、拆出按顺序执行的子 Issue；人审阅拆解结果后放行，之后由已有的主 / 子 Issue 链逐个实现、交付、评审。

现在的问题：

- 这一段完全靠人和本地 AI 完成。本仓库 008 之前的每个任务都由本地 Claude 写设计文档、拆子 Issue，再由人打 ready。
- 拆解是交付质量的上游。评审试跑（[007](../007-auto-review/README.md)）表明「新功能与已有功能相互影响」这类问题不在 diff 里，评审抓不到，只能在设计阶段识别出来并写进验收。
- 下游已经具备：主 / 子 Issue 串行门控、堆叠 PR、上游合并后变基（[005](../005-issue-chain/README.md)），文档分支（复杂方式），返工与接续（[003](../003-issue-continuity/README.md)），独立评审（007）。缺的只是生成子 Issue 的一环。

## 流程

```text
人：建需求 Issue（正文含「模式：拆解」）→ 打 workling:ready
  → workling：拆解运行（kind: plan）
      读仓库与需求 → 写设计文档并本地提交 → 产出子 Issue 清单 out/plan.json
  → 主体：校验 → 推送文档到该 Issue 的任务分支 → 创建子 Issue 并挂到需求 Issue 下 → 评论拆解结果
人：审阅文档与子 Issue（可直接编辑子 Issue）
  → 给需求 Issue 重新打 workling:ready
  → 已有逻辑：主 Issue 展开，子 Issue 按顺序执行
```

需求不清时，拆解运行改为提问（沿用答复模式），人用 `/workling <回答>` 回复后重新拆解。

## 已定的规则

1. **拆解是一次 worker 运行**（`kind: 'plan'`），与实现在同一个执行器里，不持有 GitHub 凭证。原因：要通读仓库，输入（Issue 正文）不可信。
2. **拆解只提交文档**。worker 可以本地提交设计文档；主体落地时拒绝任何非文档文件（只允许 `.md` 与常见图片），其余校验（分支命名空间、工作流、密钥扫描）沿用实现运行。
3. **文档推送到需求 Issue 自己的任务分支**（`workling/<号>-<短名>`），不建 PR。子 Issue 正文由主体加上 `分支：<该分支>` 行，因此第一个子任务从它切出，文档随第一个子任务的 PR 合入默认分支，与现有的「复杂方式：文档分支 + Issue」完全一致。没有文档提交时子 Issue 不带 `分支：` 行。
4. **子 Issue 由主体创建**，LLM 只给标题和正文；主体负责校验格式、加 `分支：` 行和来源标记、创建、挂到父 Issue、按清单顺序排列。创建过程可重入：每创建一个就落库，对账重试时跳过已创建的。
5. **人工放行是保留的关卡**。拆解完成后需求 Issue 标为 `workling:done`；人确认后重新打 `workling:ready`，此时它已有子 Issue，走已有的「主 Issue 展开」逻辑。不新增状态标签。
6. **触发方式是正文指令行 `模式：拆解`**，与 `分支：`、`模型：`、`强度：` 同一写法（中文全角冒号、单独一行、代码块和注释内的不算）。打 ready 时：有子 Issue → 展开（已有逻辑，不看指令）；没有子 Issue 且有 `模式：拆解` → 拆解运行；否则 → 实现运行。
7. **重新拆解只在没有未关闭的子 Issue 时进行**。需求 Issue 还有打开的子 Issue 时，`/workling` 不排拆解运行，主体评论说明：直接编辑子 Issue，或把子 Issue 全部关闭为「不计划」后再评论 `/workling`。自动同步已有子 Issue 留到用过之后再定（见「后续」）。
8. **拆解要识别受影响的已有功能**，写进设计文档，并把对应的回归检查写进相关子 Issue 的「验收」。这是评审抓不到的那类问题的主要防线。
9. **默认用更强的模型**。设置页新增「拆解模型 / 拆解推理强度」，未设置时用默认 codex 模型与 `high`；需求 Issue 的 `模型：`、`强度：` 行覆盖它们。
10. **只支持 GitHub**。

阶段 1 做完后，不启动主体就能用 `workling-worker` 对样例跑出设计文档和子 Issue 清单，用来调提示词和比较模型。阶段 2 做完后，线上可以完整走通「需求 Issue → 子 Issue → 逐个交付」。

两个阶段按主 / 子 Issue 串行执行；阶段 2 依赖阶段 1 的契约。

## 不做

- 不自动放行：拆解结果必须由人重新打 ready 才开始执行。
- 不评审拆解结果（不对 `plan` 运行排评审）。
- 不同步已有子 Issue（改写、新增、关闭、重排），见规则 7。
- 不跨仓库拆解；子 Issue 只建在需求 Issue 所在仓库。
- 不在全部子任务完成后自动关闭需求 Issue。
- 不在主体里直接调用 LLM 做拆解；拆解要通读仓库。

## 后续（用过之后再定）

- 已有子 Issue 时的重新拆解：按 `out/plan.json` 改写、新增、关闭、重排子 Issue，只允许在任何子任务开始执行之前。
- 对拆解结果做独立评审，或由分诊对子 Issue 打分。
- 全部子任务合入后关闭需求 Issue 并汇总。
