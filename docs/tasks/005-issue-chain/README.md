# 主 / 子 Issue 连续执行（堆叠分支）

## 目标

一个大需求拆成若干个有先后顺序的子 Issue 时（例如「控制台改版 1/4–4/4」），只需给**主 Issue** 打一次 `workling:ready`，workling 就按子 Issue 的顺序依次执行。后一个子任务基于前一个子任务的工作分支继续，各自开 PR，PR 的 base 是上一个子任务的分支，不用等前一个 PR 合并。

现在的问题：

- 子任务只能等上一个合入后再手动打 ready，一组 4 个子任务至少要人工介入 4 次。
- 提前打 ready 会白跑。比如 #49（SPA 阶段 7）在阶段 6 合入之前开跑，读完文档发现前提不满足，白白浪费一轮。

## 已定的规则

1. **顺序来源**：使用 GitHub 原生 sub-issue（`GET /repos/{owner}/{repo}/issues/{n}/sub_issues`），顺序以返回顺序（即 GitHub 上拖拽的顺序）为准。不另定义正文格式。
2. **主 Issue 不执行**：主 Issue 只作容器，不写入 `issues` 表，也不拉起任务。给它打 `workling:ready` 等于把可执行的子 Issue 全部打上 ready。
3. **串行门控**：子 Issue 只有在它的「上一个兄弟」满足条件后才会被领取，否则一直留在 queued，不占并发名额。
4. **堆叠**：上一个兄弟已完成、PR 仍开着时，本子任务从上一个兄弟的工作分支切出，PR 的 base 设为该分支；上一个兄弟已合并或已关闭为完成时，按现有规则从文档分支或默认分支切出。
5. **部分完成不放行**：上一个兄弟只交付了部分（draft PR）时，下一个子任务不开始，避免叠在不完整的基础上。
6. **失败即停**：某个子任务失败后，链条停在那里；用户修复后，那个子任务重新完成，后面的子任务自动接着跑。
7. **只支持同一仓库**：跨仓库的 sub-issue 不支持，遇到时该子任务以错误结束，错误原因写清楚。
8. **只支持 GitHub**：GitLab 暂不处理（现有轮询本来也跳过 GitLab）。

只做完阶段 1 已经能连续推进。阶段 2 解决的是：上游 PR 以 squash 方式合并后，下游 PR 的 diff 会混进上游的提交。

## 不做

- 不新增「前置：#n」之类的正文语法，顺序只看 GitHub 原生 sub-issue。
- 不做多层嵌套（子 Issue 的子 Issue），只看主 Issue 的直接子 Issue。
- 不并行执行同一个主 Issue 下的子任务。
- 分诊（triage）不做特殊处理：主 Issue 可能被分诊判为信息不全，这是已知问题，另行处理。
