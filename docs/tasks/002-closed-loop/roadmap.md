# 闭环调度路线图

> 中期目标见 [README.md](README.md)。本文把它拆成可以逐个合入的小步，每完成一步就回来更新状态，并按实际情况调整后续步骤。

## 推进规则

- **一步一个 Issue**：每一步单独可合入，合入后系统完整可用，不留半成品开关。
- **先记录、再动作**：涉及自动判断的能力，先只记录并在 Web 上展示，确认可靠后再让它真正动作。
- **每一步都有可见变化**：验收写成"能在 GitHub 或 Web 上看到什么"，不只是"代码重构完了"。
- **随时调整**：走完一个里程碑，回头看后面的步骤是否还成立，不成立就改本文。

## 总览

| 里程碑           | 目标                                  | 步骤      | 依赖          |
| ---------------- | ------------------------------------- | --------- | ------------- |
| M1 无凭证 worker | 对 GitHub 的写操作全部由主体完成      | 1.1 – 1.5 | 无            |
| M2 反馈返工      | PR / Issue 上的反馈能驱动返工         | 2.1 – 2.4 | 2.3 起依赖 M1 |
| M3 worker 独立   | worker 拥有独立的目录、镜像和版本     | 3.1 – 3.3 | M1            |
| M4 部署隔离      | worker 在独立容器里运行，访问不到主体 | 4.1 – 4.2 | M3            |
| M5 分诊          | 逐步减少人工打 ready                  | 5.1 – 5.3 | 5.1 无依赖    |

建议顺序：**1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 2.3 → 2.4 → 3.x → 4.x**。2.1、2.2、5.1 不依赖 M1，可以穿插进行，用来尽早获得反馈和数据。

## M1 无凭证 worker

做完后：worker 里不再有 GitHub token，推送、建 PR、回复全部由主体完成。这是后面返工（快进推送）和隔离的前提。

| 步骤 | 内容                                                                                                                                                                      | 做完后能看到                                                        | 状态   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ------ |
| 1.1  | **契约起步**：新建 `src/contract/`，定义 `spec.json`（带 `contract` 版本号）。主体在拉起之前读取 Issue 并下载附件，写入任务目录的 `input/`；Pi 不再运行 `workling read`   | 任务目录里出现 `spec.json` 和 `input/issue.md`；行为与现在一致      | 未开始 |
| 1.2  | **主体负责代码**：每个仓库维护镜像缓存，主体检出工作副本（包括文档分支），并新建任务分支；task 不再克隆仓库                                                               | 同一仓库第二次运行时明显变快；worker 的 `origin` 指向本地镜像       | 未开始 |
| 1.3  | **主体推送并建 PR**：Pi 只做本地提交，产出 `out/commits.bundle`、`out/pr-body.md`、`out/result.json`；主体校验后推送、建 PR（分支命名空间、拒绝改动 workflows、扫描密钥） | PR 由主体创建；在 Issue 里写入"修改 workflow"之类的注入内容会被拒绝 | 未开始 |
| 1.4  | **主体负责回复与勾选**：Pi 产出 `issue-comment.md`、`pr-comment.md`、`checklist.json`，由主体发评论、勾选待办项                                                           | 评论和勾选的效果与现在一致，但都由主体发出                          | 未开始 |
| 1.5  | **收回凭证**：不再向 worker 传 `GH_TOKEN`；LLM Key 改为通过 `secrets/llm.json` 文件下发；删除 Pi 提示词中所有 `gh` 相关步骤                                               | worker 的环境变量里看不到 GitHub token                              | 未开始 |

## M2 反馈返工

做完后：在 PR 上 request changes，或者在 Issue / PR 里写 `/workling ...`，workling 就会接着改。

| 步骤 | 内容                                                                                                                                                                                                           | 做完后能看到                                                   | 状态   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------ |
| 2.1  | **只观察**：新建 `feedback` 表；轮询 workling PR 上的 review、评论，以及 Issue 评论，识别指令前缀（`/workling`、`@账号`）；设置页新增允许名单（默认只有 token 所属账号），按名单判断作者是否可信；只记录不动作 | Web 的 Issue 详情页能看到"收到的反馈，以及是否算作指令"        | 未开始 |
| 2.2  | **失败后带补充说明重试**：Issue 处于 `failed` 时收到指令评论，就带着这条说明重新执行 implement（不需要 M1）                                                                                                    | 失败后回复 `/workling 补充：……` 就能重跑，不用改正文、重打标签 | 未开始 |
| 2.3  | **PR 返工**：新增 `rework` 类型；收到 `CHANGES_REQUESTED` 或指令时，在 PR 分支上继续提交，主体只做快进推送；每批反馈只处理一次，同一个 Issue 同时只有一个运行                                                  | PR 上 request changes 之后，自动出现新提交                     | 未开始 |
| 2.4  | **回复与上限**：主体按 `replies.json` 逐条回复（行内评论回到原线程）；自动返工轮数上限                                                                                                                         | 每条 review 意见下面都有处理说明；超过上限后会评论说明         | 未开始 |

## M3 worker 独立

做完后：worker 可以单独修改、单独发版，也可以脱离主体单独运行。

| 步骤 | 内容                                                                                                                                 | 做完后能看到                                                              | 状态   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ------ |
| 3.1  | **搬目录**：task 和 Pi 编排迁到 `worker/`，`configs/workling/` 迁入；加 lint 约束，`src/` 和 `worker/` 只能通过 `src/contract/` 交互 | 纯搬迁，行为不变                                                          | 未开始 |
| 3.2  | **单独运行**：`workling-worker run <运行目录>`；准备几个固定样例，用来对比不同提示词或模型的效果                                     | 不启动主体，也能对一个准备好的运行目录跑出 `out/`                         | 未开始 |
| 3.3  | **单独发布**：`worker/Dockerfile`；`worker-v*` tag 触发构建并发布；镜像标签声明契约版本，主体拉起前检查兼容性                        | 只发 worker 新版本、主体不动，任务也能正常执行；版本不兼容时 Web 上有提示 | 未开始 |

## M4 部署隔离

做完后：worker 运行在独立容器里，只能看到自己的运行目录，也访问不到主体。

| 步骤 | 内容                                                                                                                  | 做完后能看到                                                     | 状态   |
| ---- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------ |
| 4.1  | **rootless 与挂载**：主体通过 rootless Docker 的 socket 拉起 worker；worker 只挂载自己的运行子目录；启动时检查 cgroup | 在 worker 容器里看不到其他任务的目录                             | 未开始 |
| 4.2  | **网络与部署**：worker 使用独立网络；生产环境去掉本机进程执行器；更新 compose、systemd 部署和 README                  | 在 worker 容器里连不上主体的 7420 端口；按 README 能从零部署起来 | 未开始 |

## M5 分诊

做完后：写得清楚的 Issue 不需要人打 ready 就会开始执行。最终是否走到 5.3，取决于 5.1 积累的数据。

| 步骤 | 内容                                                                                                                | 做完后能看到                                    | 状态   |
| ---- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------ |
| 5.1  | **影子模式**：受信作者、冷静期、内容哈希、确定性检查、一次 LLM 结构化调用；只记录结论                               | Web 上并排显示"分诊结论"和"人实际做了什么"      | 未开始 |
| 5.2  | **建议级**：判定为 `needs_info` 时打标签，并按模板评论                                                              | 信息不全的 Issue 会收到"缺什么"的提示           | 未开始 |
| 5.3  | **自动级**：按仓库开启；受信作者的 Issue 判定为 `accept` 后自动入队；`workling:hold` 可以叫停；同时更新接入文档模板 | 新建一个写清楚的 Issue，不打 ready 也会开始执行 | 未开始 |

- 依赖顺序、跨机器调度、LLM 代理：见 README 第 10 节。
