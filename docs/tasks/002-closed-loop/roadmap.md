# 闭环调度路线图

> 中期目标见 [README.md](README.md)。本文把它拆成可以逐个合入的小步，并按实际情况调整后续步骤。
>
> 进度与优先级只记在 GitHub Project「[workling 路线图](https://github.com/users/tangtj/projects/4)」，本文不重复记录状态。某一步转为 Issue 后，把链接填进表格的 Issue 列。

## 推进规则

- **一步一个 Issue**：每一步单独可合入，合入后系统完整可用，不留半成品开关。
- **先记录、再动作**：涉及自动判断的能力，先只记录并在 Web 上展示，确认可靠后再让它真正动作。
- **每一步都有可见变化**：验收写成"能在 GitHub 或 Web 上看到什么"，不只是"代码重构完了"。
- **随时调整**：走完一个里程碑，回头看后面的步骤是否还成立，不成立就改本文。

## 总览

| 里程碑           | 目标                                  | 步骤      | 依赖          |
| ---------------- | ------------------------------------- | --------- | ------------- |
| M1 无凭证 worker | 对 GitHub 的写操作全部由主体完成      | 1.1 – 1.5 | 无            |
| M2 反馈返工      | PR / Issue 上的反馈能驱动返工         | 2.1 – 2.4 | 2.3 起依赖 M1 |
| M3 worker 独立   | worker 拥有独立的目录、镜像和版本     | 3.1 – 3.3 | M1            |
| M4 部署隔离      | worker 在独立容器里运行，访问不到主体 | 4.1 – 4.2 | M3            |
| M5 分诊          | 逐步减少人工打 ready                  | 5.1 – 5.3 | 5.1 无依赖    |

建议顺序：**1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 2.3 → 2.4 → 3.x → 4.x**。2.1、2.2、5.1 不依赖 M1，可以穿插进行，用来尽早获得反馈和数据。

## 与 001-web-spa 交叉推进

两条线同时推进：

- **Web 线**：[001-web-spa](../001-web-spa/README.md) 剩余阶段，只改 `src/web/`。
- **核心线**：本路线图中不涉及页面的部分，主要改 `src/serve/`、`src/task/`、`src/executor/`、`src/issue/`。

规则：

- **每条线同一时间最多一个 Issue 处于就绪或执行中**，两条线可以各有一个。同一条线内的步骤会改同一批文件，并行必然冲突。
- **002 不在旧页面上加界面**。001 的页面已全部迁移为 React，需要展示的部分（2.1 的反馈与受信账号、5.1 的分诊对照）直接加在对应 React 页面上。
- **数据库迁移**：两个在飞的 Issue 都改了 `src/db/schema.ts` 时，后合入的那个要基于最新的默认分支重新生成迁移文件。

## M1 无凭证 worker

做完后：worker 里不再有 GitHub token，推送、建 PR、回复全部由主体完成。这是后面返工（快进推送）和隔离的前提。

| 步骤 | 内容                                                                                                                                                                                                            | 做完后能看到                                                          | Issue                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------- |
| 1.1  | **契约起步**：新建 `src/contract/`，定义 `spec.json`（带 `contract` 版本号）。主体在拉起之前读取 Issue 并下载附件，写入任务目录的 `input/`；Pi 不再运行 `workling read`                                         | 任务目录里出现 `spec.json` 和 `input/issue.md`；行为与现在一致        | [#41](https://github.com/tangtj/workling/issues/41) |
| 1.2  | **主体负责代码**：每个仓库维护镜像缓存，主体检出工作副本（包括文档分支），并新建任务分支；task 不再克隆仓库                                                                                                     | 同一仓库第二次运行明显变快；`分支：` 写错时由主体直接判失败并评论原因 | [#42](https://github.com/tangtj/workling/issues/42) |
| 1.3  | **主体推送并建 PR**：Pi 只做本地提交，产出 `out/commits.bundle`、`out/pr-body.md`、`out/result.json`；主体校验后推送、建 PR（分支命名空间、拒绝改动 workflows、扫描密钥）。工作副本的 `origin` 改为指向本地镜像 | PR 由主体创建；在 Issue 里写入"修改 workflow"之类的注入内容会被拒绝   | [#53](https://github.com/tangtj/workling/issues/53) |
| 1.4  | **主体负责回复与勾选**：Pi 产出 `issue-comment.md`、`checklist.json`，由主体发评论、勾选待办项                                                                                                                  | 评论和勾选的效果与现在一致，但都由主体发出                            | [#55](https://github.com/tangtj/workling/issues/55) |
| 1.5  | **收回凭证**：不再向 worker 传 `GH_TOKEN`；LLM Key 改为通过 `secrets/llm.json` 文件下发；删除 Pi 提示词中所有 `gh` 相关步骤                                                                                     | worker 的环境变量里看不到 GitHub token                                | [#64](https://github.com/tangtj/workling/issues/64) |

## M2 反馈返工

做完后：在 PR 上 request changes，或者在 Issue / PR 里写 `/workling ...`，workling 就会接着改。

> [003-issue-continuity](../003-issue-continuity/README.md) 已实现：一个 Issue 一条持续分支、`/workling` 对失败和 PR 仍开着的 Issue 接续、上下文包与答复模式。2.2 已被覆盖；2.3 剩下的是「PR review 触发返工」。

| 步骤 | 内容                                                                                                                                                                                                                                                                                                                   | 做完后能看到                                                   | Issue                                               |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| 2.1  | **只观察**：新建 `feedback`、`feedback_cursors`、`trusted_users` 表；增量轮询 workling PR 上的 review、评论和 Issue 评论；按写权限与受信账号判定作者，识别指令前缀（沿用 `/workling`、`@<token 账号>`）；只记录不动作。仓库详情页配置受信账号，Issue 详情页展示反馈。详见 [step-2.1-feedback.md](step-2.1-feedback.md) | 在 Issue 详情页能看到收到的反馈、作者是否可信、是否算作指令    | [#67](https://github.com/tangtj/workling/issues/67) |
| 2.2  | **失败后带补充说明重试**：Issue 处于 `failed` 时收到指令评论，就带着这条说明重新执行 implement（不需要 M1）                                                                                                                                                                                                            | 失败后回复 `/workling 补充：……` 就能重跑，不用改正文、重打标签 | [#38](https://github.com/tangtj/workling/issues/38) |
| 2.3  | **PR 返工**：新增 `rework` 类型；收到 `CHANGES_REQUESTED` 或指令时，在 PR 分支上继续提交，主体只做快进推送；每批反馈只处理一次，同一个 Issue 同时只有一个运行                                                                                                                                                          | PR 上 request changes 之后，自动出现新提交                     | —                                                   |
| 2.4  | **回复与上限**：主体按 `replies.json` 逐条回复（行内评论回到原线程）；自动返工轮数上限                                                                                                                                                                                                                                 | 每条 review 意见下面都有处理说明；超过上限后会评论说明         | —                                                   |

| 步骤 | 内容                                                                                                                  | 做完后能看到                                                     | Issue |
| ---- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ----- |
| 4.1  | **rootless 与挂载**：主体通过 rootless Docker 的 socket 拉起 worker；worker 只挂载自己的运行子目录；启动时检查 cgroup | 在 worker 容器里看不到其他任务的目录                             | —     |
| 4.2  | **网络与部署**：worker 使用独立网络；生产环境去掉本机进程执行器；更新 compose、systemd 部署和 README                  | 在 worker 容器里连不上主体的 7420 端口；按 README 能从零部署起来 | —     |
