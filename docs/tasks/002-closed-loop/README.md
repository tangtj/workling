# 闭环调度：中期目标

> 状态：草案 v3（2026-11-18），待评审。本文描述的是**中期目标**，不是一次性实施的方案；拆解后的小步计划与进度见 [roadmap.md](roadmap.md)。第 9 节的阶段划分以路线图为准。

## 1. 背景

现在的 workling 由两部分组成：

- `workling serve`：轮询带 `workling:ready` 标签的 Issue，入队、拉起 task、对账、改标签，同时提供 Web 管理界面。
- `workling task`：克隆业务仓库并拉起 Pi。Pi 读取 Issue、调用 codex 改代码，然后**由它自己**完成提交、推送、建 PR、回复 Issue 和 PR、勾选 Issue 待办项。

存在的问题：

1. **流程不闭环**：开出 PR 就算结束了。PR 上的 review 意见、Issue 里补充的说明，都要人改完 Issue 正文后重新打 ready 才能返工。
2. **worker 持有可写的仓库 token**：被提示注入的 Issue，或者仓库里的恶意安装脚本和测试，可以把 token 发到外网，或者推送任意分支。
3. **worker 和主体耦合在一起**：task 的代码、Pi 的提示词和主体在同一个代码树、同一个镜像里，跟着同一个版本发布。想改进 worker 的效果，只能连主体一起发布。
4. **每个 Issue 都要人手动打 `workling:ready`**。最终目标是让主体自己判断，但不可能一步做到。

## 2. 目标与不做

目标：

- **调度主体**负责闭环：扫描 → 判断状态变化 → 派发执行 → 落地结果 → 根据反馈继续推进。**对 GitHub 的写操作只由主体完成。**
- **worker 是独立组件**：和主体在同一个代码仓库里，但有自己的目录、镜像和版本号，可以独立迭代；它和主体之间只靠一份带版本号的契约交接。worker 不持有任何 GitHub 凭证。
- 第一批闭环能力：**PR / Issue 反馈返工**。
- 分诊**分级逐步放开**：先只记录不动作（影子模式），再给建议，最后才在受信范围内自动开始。
- worker 运行在独立容器里（rootless Docker）。主体放进容器只是为了部署方便，不算安全边界。

不做：

- 不拆仓库。
- 不做依赖顺序，也不做其他编排（多分支叠加、跨仓库、按文件互斥等），以后遇到再说。
- 不引入 HTTP 回调、消息中间件，也不做跨机器调度（第 10 节只写演进路线）。
- 不改 codex 的用法。

## 3. 设计原则

1. **按状态驱动，不按事件驱动**。主体只能轮询（管理端口只对本机开放，接不了 webhook），漏掉事件是常态。每一轮都根据"GitHub 上看到的现状 + 库里记录的状态"重新计算该做什么，所有动作都要幂等。这样主体重启、某一轮失败、有人改了标签，下一轮都能自己纠正回来。
2. **观察、决策、执行分开**。决策写成纯函数：输入现状，输出要执行的动作，用表驱动的用例测试。执行部分只负责调用 GitHub 和执行器。现有的 `poll` / `launch` / `reconcile` 按这个思路逐步整理，**不新建框架**。
3. **信任来自人，不来自文字**。Issue 正文、评论、PR 内容都是不可信输入。一段文字能不能触发执行，看作者是谁，而不是看内容怎么写。
4. **LLM 只给结论，动作由确定性代码执行**。LLM 输出枚举值和结构化字段；改标签、入队、发评论都由主体按规则完成，评论正文以模板为主。
5. **自动化分级放开**。每项自动判断都先在影子模式下运行，把"机器会怎么做"和"人实际怎么做"记录下来做对比；数据说明靠得住了，再按仓库逐级打开。

## 4. 总体结构

```text
                          GitHub
                   ▲ 所有写操作：标签 / 评论 / 推送 / PR
                   │
┌──────────────────┴─────────────────────────────┐
│ 调度主体  workling serve（容器或宿主机进程）     │
│                                                  │
│  观察：Issue（增量）、Issue 评论、workling PR 的   │
│        review / 评论 / 状态                       │
│  决策：入队、返工判定、分诊（影子 / 建议 / 自动）   │
│  执行：准备工作区 → 拉起 worker → 校验并落地结果    │
│  仓库镜像缓存（持有 token，只在主体内使用）        │
│  SQLite、运行日志、管理界面 127.0.0.1:7420        │
└───────────────┬──────────────────────────────────┘
                │ rootless Docker socket：启动 / 查询 / 结束
                │ 运行目录：spec.json 与工作副本进入，out/ 返回
┌───────────────▼──────────────────────────────────┐
│ worker 容器（独立镜像、独立版本，每次运行一个）     │
│  Pi → codex：读代码、改代码、本地提交               │
│  不持有 GitHub 凭证；能出网（LLM、包管理源）；       │
│  访问不到主体                                      │
└────────────────────────────────────────────────────┘
```

## 5. worker：独立组件

### 5.1 边界

worker 只关心"在给定的工作副本上，按 spec 完成一项工作，把产出写进 `out/`"。它不知道 GitHub、标签、数据库，也不知道主体的存在。

带来的好处：

- worker 可以**单独运行**：`workling-worker run <运行目录>`。给它一个准备好的运行目录就能执行，方便开发和评估 worker 的效果（例如固定一组样例，比较不同提示词或模型的表现），不需要启动主体。
- worker 的提示词、Pi 扩展、codex 调用方式可以频繁调整，单独发布镜像即可，不影响主体。

### 5.2 代码组织

仍然在同一个仓库里，按目录划清边界：

```text
src/            主体（serve、Web、调度、落地）
src/contract/   契约：spec 与产出的 typebox schema、契约版本号。主体与 worker 都引用这里
worker/         worker：入口、Pi 编排、提示词（由 configs/workling/ 迁入）、Pi 扩展、测试
worker/Dockerfile
```

- 用 lint 规则约束依赖方向：`worker/` 和 `src/` 互相不能引用，只能共同引用 `src/contract/`。
- 依赖暂时仍然放在根目录的 `package.json` 里。如果以后两边的依赖差异变大（主体不再需要 `pi-coding-agent`，worker 不需要 Hono 和 React），再改成 Bun workspaces。这一步不影响契约。

### 5.3 版本与兼容

- 契约有一个整数版本号（`contract`）。worker 镜像通过镜像标签声明自己实现的契约版本（`LABEL workling.contract=1`）。
- 主体声明自己支持的契约版本范围。拉起之前，用 `docker image inspect` 检查 worker 镜像的标签，不兼容就不拉起，在 Web 上提示。
- worker 镜像用独立的 `worker-v*` tag 触发构建和发布，和主体的发布流程互不影响，在设置页里选择镜像（沿用现在的 `taskImage`）。主体的在线更新不影响 worker，worker 的更新也不需要重启主体。
- 契约变更规则：只新增可选字段时不升版本；删除字段或改变字段语义时升版本，并且主体在一个过渡期内同时支持新旧两个版本。

### 5.4 契约

运行目录的结构：

```text
<运行目录>/
  spec.json        主体写入：任务描述
  input/           主体写入：issue.md、附件、feedback.md（返工时）
  repo/            主体检出的工作副本，origin 指向本地镜像，不带凭证
  secrets/llm.json 主体写入，权限 600：LLM 接入信息（不放进环境变量，docker inspect 能看到环境变量）
  events.jsonl     worker 追加：进度事件
  out/             worker 写入：产出
```

`spec.json`：

```ts
type Spec = {
  contract: 1
  kind: 'implement' | 'rework' | 'review' // review 先预留，暂不实现
  issue: { ref: string; title: string } // 只用于展示和提交信息，正文在 input/issue.md
  repo: { baseRef: string; branch: string } // 工作副本已经检出到 branch
  model: { codex: string; effort: string; pi?: string }
  git: { name: string; email: string }
}
```

`out/`：

| 文件               | 内容                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `result.json`      | 必有：`contract: 1`、`outcome: 'completed' \| 'partial' \| 'incomplete'`、`branch: string`、`head: string \| null`（与 `baseRef` 相同时为 `null`）、`commits: number`（`baseRef..head` 的提交数） |
| `commits.bundle`   | 相对 `baseRef` 的新提交（`git bundle`）；`commits > 0` 时产出                                                                                                                                     |
| `pr-body.md`       | 有提交时由 Pi 写入的 PR 正文（`implement`）                                                                                                                                                       |
| `issue-comment.md` | Issue 回复                                                                                                                                                                                        |
| `pr-comment.md`    | 可选：PR 下的核对结论                                                                                                                                                                             |
| `checklist.json`   | 待办项的勾选变更：`[{ line, checked, evidence }]`                                                                                                                                                 |
| `replies.json`     | 对反馈的逐条回复：`[{ feedbackId, body }]`（`rework`）                                                                                                                                            |
| `review.json`      | review 意见：总体意见 + 行内意见（`review`）                                                                                                                                                      |

## 6. 主体

### 6.1 状态与标签

工作项仍以 Issue 为单位（沿用 `issues` 表），PR 挂在 Issue 下面。

```text
ready（人）──▶ queued ──▶ running(implement) ──┬─▶ failed ──（人补充反馈）──▶ queued(rework 或 implement)
                                                ▼
                                            pr_open ──（有新的可执行反馈）──▶ queued(rework) ──▶ running(rework) ─┐
                                                ▲                                                                │
                                                └────────────────────────────────────────────────────────────────┘
                                                ├─▶ merged
                                                └─▶ closed
任何阶段：人打上 workling:hold 后，主体暂停自动推进
```

| 标签                          | 含义                                          | 由谁打 |
| ----------------------------- | --------------------------------------------- | ------ |
| `workling:ready`              | 开始执行（现阶段仍然是唯一的入口）            | 人     |
| `workling:hold`               | 暂停：主体不再自动推进这个 Issue，包括返工    | 人     |
| `workling:queued` / `running` | 同现在；返工时也会回到这两个状态              | 主体   |
| `workling:done` / `failed`    | `done` 表示 PR 已开出，是否合入以 PR 状态为准 | 主体   |
| `workling:needs-info`         | 分诊到"建议"级以上才会使用（6.4）             | 主体   |

### 6.2 准备工作区与落地

**准备**（在主体里进行，持有 token）：

1. 每个仓库维护一份镜像缓存（`git clone --mirror`），每次运行前 fetch。
2. 从镜像检出工作副本：
   - `implement`：基于默认分支，或基于文档分支（`分支：` 行）新建 `workling/<号>-<短名>`。
   - `rework`：检出 PR 分支的最新提交。
   - `review`：检出 PR 的 head。
3. 写入 `spec.json`、`input/`、`secrets/`。现在 `workling read` 负责的 Issue 与附件下载，搬到这一步来做。

**落地**（确定性代码，逐项校验）：

主体不在 worker 的工作副本中运行 Git。主体在独立的 bare 仓库中导入并校验提交包，分支和基点以数据库中准备工作副本时记录的值为准。

- **推送**：只能推到 `workling/<号>-*` 命名空间。`implement` 新建分支；`rework` 只允许快进，如果运行期间有人往 PR 分支推了提交，快进会失败，这时重新排队。禁止推送默认分支和文档分支。
- **改动范围**：bundle 里只要有提交改到 `.github/workflows/`，默认拒绝（可以按仓库放开），防止借 CI 拿到仓库 Secrets。
- **大小与内容**：限制 bundle 和各个文本文件的大小；推送前扫描已知密钥，命中就拒绝。
- **文本**：PR 正文和评论由主体发出，去掉其中的 `@` 提及，避免被注入后去打扰别人。
- **待办勾选**：主体按 `checklist.json` 执行现在 Pi 做的那套流程（先评论，再按原文行替换），原文行对不上的跳过。
- 任何一项校验失败，整次运行判为失败并评论说明原因，不做部分落地。

### 6.3 反馈返工

> 已确认（2026-11-18）。

**信任规则**（已确认）：只认**允许名单**里的 GitHub 账号。名单在设置页维护，默认只有仓库 token 所属的账号（通过 `gh api user` 取得）；仓库有多少协作者都不影响。名单对返工指令、review 和分诊统一生效。人手动打 `workling:ready` 不受名单限制，因为能不能打标签由 GitHub 的权限控制。

**反馈来源**（只认允许名单里的作者）：

| 来源                                                | 现阶段如何触发                                                           |
| --------------------------------------------------- | ------------------------------------------------------------------------ |
| workling PR 上的 review，状态为 `CHANGES_REQUESTED` | **自动**触发返工。这个状态本身就是明确的"请修改"信号                     |
| workling PR 上的普通评论、行内评论                  | 评论以指令前缀开头才触发，其后的文字作为本次的指令                       |
| Issue 评论（PR 已开出或运行失败之后）               | 同上，以指令前缀开头才触发；运行失败后发指令等价于"带着这条补充说明重试" |
| 修改 Issue 正文后重新打 `workling:ready`            | 保留现有行为                                                             |

指令前缀两种都支持：`/workling`，以及 `@<workling 所用 token 的账号>`。只认评论开头的前缀，正文中间出现的不算。

普通评论默认不触发，因为讨论和指令现在分不清。以后用 LLM 识别评论意图，同样按影子 → 建议 → 自动三级放开（见 6.4）。

**规则**：

- 以批次为单位：一次 review，或者一轮轮询中收集到的所有指令评论，合并成一次返工，写进 `input/feedback.md`。每条反馈带 `feedbackId`、作者、文件和行号（如果有）。
- 记录已经处理过的反馈 ID，不重复处理。
- 同一个 Issue 同时只能有一个运行。运行期间新来的反馈，留到下一批。
- 每个 PR 最多自动返工 3 轮（可配置），超过后评论说明，等人处理。用指令显式触发的不受这个限制。
- workling 自己产出的 review（`review` 类型）不触发返工，避免和自己来回循环。
- PR 合入或关闭之后，评论不再触发返工；新的需求另开 Issue。
- 落地时，主体按 `replies.json` 逐条回复反馈：PR 行内评论回在原评论的线程里，其他的汇总成一条评论。

### 6.4 分诊：分级放开

最终目标是不用人打 ready。按仓库设置分诊级别，逐级打开：

| 级别 | 行为                                                                                                                      | 进入下一级的依据                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 关闭 | 和现在一样                                                                                                                | —                                      |
| 影子 | 对新建或修改过的 Issue 做分诊，**只记录在库里**，在 Web 上和人的实际操作（是否打了 ready、多久后打的）对照显示            | 一段时间内，分诊结论和人的判断基本一致 |
| 建议 | 判定为 `needs_info` 时，打 `workling:needs-info` 标签并用模板评论缺什么；判定为 `accept` 时不做任何动作，仍然等人打 ready | 人基本不再修改它的建议                 |
| 自动 | 受信作者的 Issue 判定为 `accept` 后，过了冷静期就自动入队；`workling:hold` 可以随时叫停                                   | —                                      |

不管哪一级都遵守：

- 只有作者在允许名单里（见 6.3）时才会被分诊。其他人的 Issue 只能由人手动打 ready。这条是安全边界，不交给 LLM。
- Issue 最后一次修改之后要过冷静期（默认 10 分钟）才分诊，内容哈希没变就不重复分诊。
- 先做确定性检查（有没有 `## 目标`、`## 验收`，各指令行的格式），再做一次 LLM 结构化调用（`pi-ai`，不用 agent 循环）。输出是 `{ decision: 'accept' | 'needs_info' | 'ignore', missing: string[], note: string }`，其中 `note` 只存库，不发到 GitHub。
- LLM 失败或输出无效时保持原状，下一轮再试，不默认放行。
- 判定为 `ignore` 时什么都不做。很多 Issue 只是备忘，不应该被打扰。

## 7. 部署与隔离

- **宿主机**：用一个专用的普通用户运行 rootless Docker。
- **主体**：可以运行在容器里（挂载 rootless socket 和数据卷），也可以作为宿主机上的 systemd 进程，按部署习惯选。管理端口只发布到 `127.0.0.1:7420`。
- **worker**：由主体通过 socket 启动，沿用现有的加固参数（`--cap-drop ALL`、`no-new-privileges`、资源限制、非 root 用户）。
  - 只挂载属于本次运行的子目录（Docker 的 `volume-subpath`，需要确认部署环境的 Docker 版本支持；不支持时退回到绑定挂载宿主机目录）。
  - 使用独立网络，可以出网，但**没有到主体的路由**。
- **生产环境去掉"本机进程"执行器**，只在开发时使用。README 里"worker 和主体在同一个容器"的推荐部署方式删掉。
- rootless 模式下，CPU 和内存限制依赖 cgroup v2 与 systemd delegation，启动时检查，不满足就给出明确提示。
- 不用 Docker in Docker（它需要 `--privileged`），也不挂载 rootful 的 `docker.sock`。

## 8. 数据结构变更

用 drizzle 迁移：

- `issues`：`status` 不新增取值，`pr_open` 用现有的 `done` 加 `prState` 表达；新增 `triage`（JSON：级别、结论、内容哈希、时间）和 `reworkRounds`。
- `runs`：新增 `kind` 和 `contract`。
- 新增 `feedback` 表：`issueId`、来源（PR review / PR 评论 / Issue 评论）、GitHub 上的 ID、作者、正文摘要、状态（待处理 / 已纳入运行 / 已回复）、`runId`。
- 设置项：worker 镜像（沿用 `taskImage`）、返工轮数上限、按仓库的分诊级别、允许名单、冷静期。

## 9. 阶段

每个阶段对应一个 workling Issue，开始前补充该阶段的详细文档。

| 阶段 | 内容                                                                                                                                                                                                  | 依赖                   |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| 1    | 契约与主体落地：建立 `src/contract/`；主体负责准备工作区（镜像缓存、`spec.json`、`input/`），worker 产出 `out/`，由主体校验后推送、建 PR、回复、勾选；worker 不再持有 token。先在本机进程执行器上完成 | 无                     |
| 2    | worker 独立：迁到 `worker/` 目录，配套 lint 依赖约束、单独的 Dockerfile 和 `worker-v*` 发布流程、契约版本检查、`workling-worker run` 单独运行                                                         | 阶段 1                 |
| 3    | 部署隔离：rootless Docker、worker 只挂运行子目录、独立网络、去掉生产环境的本机进程执行器；更新 compose、systemd 部署和 README                                                                         | 阶段 2                 |
| 4    | 反馈返工：`feedback` 表、观察 PR review 和评论以及 Issue 评论、`/workling` 指令、`rework` 类型、快进推送、逐条回复、轮数上限                                                                          | 阶段 1                 |

- 阶段 1 是后面所有阶段的基础，必须先做。
- 阶段 4 和阶段 2、3 改动面基本不重叠（阶段 4 在主体的观察与决策部分，阶段 2、3 在 worker 目录、镜像和部署），阶段 1 完成后可以并行。
- 阶段 5 不依赖其他阶段，可以和阶段 1 并行。
- 所有阶段都会改 `src/db/schema.ts`，迁移文件按合入顺序重新生成。

## 10. 演进路线（本次不实现）

- **跨机器**：worker 不需要凭证，只要拿到运行目录并交回 `out/`，所以跨机器只是"运行目录怎么传过去"的问题。第一步用 `DOCKER_HOST=ssh://` 加目录同步；之后可以演进为远端守护进程主动领取任务。契约不需要变。
- **更多反馈来源**：CI 失败、与默认分支冲突时自动 rebase、用 LLM 识别评论意图，都接入同一套"观察 → 决策 → 执行"流程。
- **依赖顺序**：`依赖：` 行、被依赖的 PR 合入后才放行、文档分支合并默认分支。
- **LLM 代理**：如果要让 worker 连 LLM Key 都拿不到，可以由主体做代理；代价是 worker 需要能访问主体，暂时不做。
