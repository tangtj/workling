# Issue 评论改版

## 目标

让人打开 Issue 就能看懂 workling 做到哪一步、每一轮的结果是什么、下一步该谁做什么。

现在的问题（对照 #112、#116、#121、#126 的评论）：

- **看不出流程顺序**。每条评论都是孤立的，没有轮次，也不说下一步。一次运行固定发 3 条（领取、交付、「即将更新 Issue 待办」），第三条说的是「即将」，却发在交付之后。
- **执行上下文不对**。领取评论写的是机器名、服务器上的任务目录和 UTC 时间戳，读者用不上；轮次、运行类型、分支、用时、由谁实现这些有用的信息反而没有。
- **格式不统一**。交付评论的正文由 Pi 自由写，段落、`##`、`###` 混用，「检查」有时叫「验证」；提交号的写法每次不同。待办评论把 `- [ ] ...` 原文整行嵌在列表里，很难读。

## 已定的规则

1. **外框由 workling 写，正文由 AI 写**。外框是标题行（轮次 · 类型 · 结果）、事实行（PR、提交数、用时等）和「下一步」，全部从数据库和落地结果生成。正文由 Pi 决定写什么、写多少，workling 只给写作方向，不给逐节模板。
2. **事实不让 AI 复述**。交付结果、PR 链接、提交号、用时、如何重试都在外框里，正文不再写。
3. **正文靠约束保持整齐**：小节可选，但小节名只能从固定词表里选、顺序固定；小节标题统一用加粗；有长度预算，超出的放进 `<details>`；提示词里给范例。
4. **workling 对正文只做格式整理**：标题降级为加粗、去掉开头重复的结果行、压缩空行。不改写内容。
5. **一次运行只发一条结果评论**。待办勾选的说明并入这条评论，不再单发；仍然是先发评论、再修改 Issue 正文。
6. **进度原地更新，结果单独发**。每个 Issue 有一条进度评论，列出每一轮的类型、结果、PR 和用时，状态变化时编辑这条评论；需要人看的结果仍然新发评论。有了进度评论后不再发领取评论。
7. 评论里不出现机器名和服务器路径；需要定位时写运行编号（`运行 #<id>`），在控制台里查。

## 分阶段

| 阶段 | 内容                                                                                   | 文档                                                       |
| ---- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 1    | 评论外框、正文整理、待办并入交付评论、领取 / 答复 / 拆解 / 失败评论改版、Pi 的写作约定 | [stage-1-run-comments.md](stage-1-run-comments.md)         |
| 2    | 进度评论：创建、原地更新、取代领取评论                                                 | [stage-2-progress-comment.md](stage-2-progress-comment.md) |

两个阶段按主 / 子 Issue 串行执行；阶段 2 依赖阶段 1 的外框与文案。

## 不做

- 不改 PR 下的评论（核对结论、反馈处理说明、行内回复）和 PR 正文。
- 不改分诊评论、上游合并后的变基提示、「不再重新拆解」等单句提示的文案。
- 不把评审结论发到 GitHub（影子级评审仍然只在控制台展示）。
- 不在评论里放控制台链接（没有对外地址的配置）。
- 不回溯修改已发出的历史评论。
