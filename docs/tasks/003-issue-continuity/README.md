# Issue 持续推进：成果不丢、上下文连续

> 本地直接实现（用户要求，不走 workling Issue）。起因是 [#67](https://github.com/tangtj/workling/issues/67)（闭环 2.1）连续 4 轮"执行未完成"，复盘后发现是流程问题，不是单次运气。A、B、C 已一次实现，与 [002 路线图](../002-closed-loop/roadmap.md) 的关系见「已定的规则」第 9 条。

## 一、发生了什么

| 轮次 | 触发                                              | 实际产出                                             | workling 的处理             |
| ---- | ------------------------------------------------- | ---------------------------------------------------- | --------------------------- |
| 1    | 打 `workling:ready`                               | 表、迁移、反馈观察初版、评论标记、部分测试           | 判 incomplete，提交丢弃     |
| 2    | 重打 ready                                        | 同上重做一遍，本地提交 `eb6ea81`                     | 判 incomplete，提交丢弃     |
| 3    | `/workling 列举一下那些还有问题进行回复`          | 按要求列出 7 条问题；找不到 `eb6ea81`                | 判"执行未完成"              |
| 4    | `/workling 你检查内容的时候是否有承接原来的分支?` | 自己翻 `/data/tasks/` 找回前两轮成果，提交 `3ac4a98` | 判 incomplete，提交再次丢弃 |

四轮约 50 分钟，最终远端什么都没有，第 2、4 轮还在重做前一轮已做过的事。

## 二、问题

### P1 成果会丢

- **结果误判**：outcome 由 [`reportResultLine`](../../../src/task/summary.ts) 从 `report.md` 用正则解析，只认单行 `结果：xxx`，且必须**恰好等于** `部分完成`。codex 实际写的是 `# 结果\n\n部分完成。尚不能…`，于是落到 `incomplete`，[land.ts](../../../src/serve/land.ts) 直接返回，bundle 不导入、不推送。
- **判定权不在 Pi**：[configs/workling/AGENTS.md](../../../configs/workling/AGENTS.md) 让 Pi"以你的核对为准"确定交付结果，但 workling 不读这个结论。
- **incomplete 没有出口**：即使判定正确，"未完成但有提交"也只能留在 worker 的任务目录里。
- **重试从零开始**：[launch.ts](../../../src/serve/launch.ts) 每轮都从文档分支或默认分支新建同名任务分支，上一轮的提交与本轮无关。
- **同名分支冲突**（修好上面之后会遇到）：第一轮推送了 `workling/67-…`，第二轮从基点重开得到不同的 tip，land 会报"远端已存在同名分支"。

### P2 上下文断了

Pi 只拿得到 `input/issue.md`（正文 + 评论）。下面这些都看不到：

- 历次运行：每轮的结果、`report.md`、Pi 的说明、做了哪些提交；
- 工作分支：已有提交、相对基点的改动；
- PR：正文、review、行内评论、CI 结论；
- 文档分支：只给了分支名，读哪些文档靠 Issue 正文自己写。

第 3 轮因此说"`eb6ea81` 不存在"；第 4 轮能找回，是因为 worker 能读到别的任务目录——这本身是隔离漏洞，不能当成接续手段。

### P3 流程太死板

- **只有一种模式**：任何 `/workling` 都走完整实现流程。第 3 轮用户只是要一份问题清单，跑了完整流程，完成了却挂"执行未完成"。
- **原样转述**：Pi 被要求把 Issue 原样复制给 codex、不改写不补充。初衷是防止 Pi 自己发明需求，但结果是 codex 每轮都拿到"从头做 2.1"，而不是"接着做，上轮缺这几项"。
- **失败评论截断**：[reconcile.ts](../../../src/serve/reconcile.ts) 只引用 `report.md` 前 20 行，最关键的"未完成与存疑"被截掉（#67 第 1 条失败评论）。

### P4 Issue 粒度（不是本文要改的，但放大了上面的问题）

#67 一次包含表、轮询、信任判定、评论标记、API、两个页面和专项测试，单轮 11–23 分钟只能出初版。粒度大时更依赖"多轮接续"，P1/P2 的代价就更明显。

## 三、想法

核心：**把 Issue 当成一条持续推进的工作线，每次运行只是在这条线上往前走一步。**

### A. 一个 Issue 一条工作分支（解决 P1）

- 工作分支 `workling/<号>-<短名>` 是 Issue 的长期状态，第一次运行从文档分支或默认分支切出，**之后每轮都从它的远端 tip 起步**。
- **只要有提交就推送**，与 outcome 无关；主体侧的安全检查（命名空间、workflow、密钥扫描、只允许快进）照旧。
- PR 随结果变化：部分完成 / 未完成但有提交 → draft PR；完成 → 转 ready。
- outcome 改由 Pi 写进 `out/result.json`（字段已存在，只是现在由 task 解析 `report.md` 填）。`report.md` 的结果仅作参考。

与路线图的关系：2.3「PR 返工：在 PR 分支上继续提交，主体只做快进推送」本质上是同一件事，但只覆盖"已有 PR 之后"。A 把它提前到第一轮，失败 / 部分完成也走同一条路。

### B. 主体组装上下文包（解决 P2）

全部由主体拉取后写入 `input/`，worker 仍不联网、不持有 token，与 M1 方向一致：

| 文件        | 内容                                                                     |
| ----------- | ------------------------------------------------------------------------ |
| `issue.md`  | 正文 + 全部评论（已有）                                                  |
| `runs.md`   | 历次运行：时间、触发评论、outcome、`report.md` 全文、Pi 的说明、提交列表 |
| `branch.md` | 工作分支 `base..tip` 的 log 与 diff stat；基点已前进时注明落后多少       |
| `pr.md`     | PR 正文、review、行内评论（带文件和行号）、CI 结论                       |
| `docs.md`   | 文档分支名及其相对默认分支新增 / 修改的文档清单                          |

`runs.md` 的数据来自主体的 runs 表与各任务目录，主体本来就在读这些文件（reconcile 发失败评论时）。有了 B，可以顺手收紧 worker 对其他任务目录的读权限。

### C. Pi 负责理解，不只是转述（解决 P3）

- **模式**：Pi 读完上下文后按最新指令选择：
  - `implement`：现有流程，加上"接着做"；
  - `answer`：只读分析后写 `out/issue-comment.md`，不调用会改文件的 codex，outcome 记为 `answered`，标签和评论文案不再显示"未完成"。
- **本轮简报**：codex 输入在原样附上 Issue 正文的基础上，增加一段由 Pi 写、明确标注的"本轮简报"——已有进度、上轮遗留问题、本轮目标（以最新 `/workling` 为准）、哪些已有改动需要保留。正文仍原样，防止需求被改写；简报只回答"现在走到哪、这轮做什么"。
- **失败评论**：引用 `report.md` 时优先保留"未完成与存疑"一节，而不是取前 20 行。

## 四、已定的规则

1. **结果**：Pi 把交付结果写到 `out/outcome.json`；缺失或无效时才回退解析 `report.md`（兼容标题格式和带尾句的写法）。有提交但结果为未完成时按部分完成落地。
2. **分支**：上一次运行的分支在镜像中存在，且 Issue 的 PR 为空或仍 open 时，从该分支末端接续；否则从文档分支或默认分支重开，同名分支已存在时加 `-<运行号>` 后缀。
3. **推送**：远端分支等于本次基点时快进推送；等于本次末端视为已推送；其他情况判失败，不强推。
4. **PR**：部分完成建 draft PR；已有 open PR 时用本次 `pr-body.md` 更新标题和正文，完成时转为 ready，并发 PR 评论。
5. **基点前进**：不自动 rebase，只在 `branch.md` 写明落后情况。
6. **从头来**：关闭（或合并）PR 后重打 ready，即从基点重开。
7. **重试入口**：`/workling` 评论除 `failed` 外，也对 PR 仍 open 的 `done` Issue 生效。
8. **答复模式**：由 Pi 按最新指令判断，不要求额外前缀。
9. **与路线图**：本文的 A 覆盖 002 的 2.2 增强和 2.3 的分支部分；2.3 剩下的「PR review 触发返工」仍按路线图推进。
